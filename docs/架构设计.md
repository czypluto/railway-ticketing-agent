# 铁路购票系统 · 架构设计

> 本文描述**代码当前的实现**，不写规划中的设计。改动代码前先读本文；若文档与代码不一致，以代码为准并同步修本文。

## 1. 定位

用户以自然语言完成查票、下单、支付的铁路购票平台。核心命题是两件事：

1. **高并发购票的一致性**——不超卖、不重复扣票、座次不冲突。
2. **把模型关进笼子**——模型只负责理解意图和组织语言，真正改数据的动作由确定性代码执行。

## 2. 服务组成

| 服务 | 技术 | 端口 | 职责 |
|---|---|---|---|
| `backend-java` | Spring Boot 3.4 / JDK 17 | 8080 | JWT 签发与校验、购票交易核心、铁路数据管理、审计 |
| `backend-python` | FastAPI | 8000 | JWT 中间件、模型路由、Agent 编排、RAG、SSE |
| 嵌入服务 `app/embed` | FastAPI + transformers | 8001 | 本地文本/图片嵌入，OpenAI 兼容 `/v1/embeddings` |

| Redis | Docker（WSL2 内） | 6379 | 余票缓存、Lua 脚本、分布式锁、Stream、令牌桶、会话记忆 |
| MySQL 8 | Docker（WSL2 内） | 3306 | 用户、铁路数据、订单、联系人、审计日志 |
| Milvus Lite | 嵌入式，随 Python 进程 | — | 向量存储与检索（`data/rag.db`） |

## 3. 两条链路

### 3.1 确定性交易链路（Java）

```
POST /api/ticket/buy
  → 令牌桶限流（Redis + Lua，QPS=1000）
  → 幂等：Redisson 锁 rv:req:{requestId} + 唯一索引
  → 车次级「一人一票」：Redis SETNX (user, trip) 原子准入
  → Redis + Lua 原子扣库存
  → 座位号分配：Redis 原子 INCR（已分配的座不重复）
  → 返回 requestId，订单经 Redis Stream 异步落库
```

**关键机制**

| 机制 | 解决的问题 |
|---|---|
| 余票预热（按「总席位 − 在售订单」回填） | 服务重启后余票丢失导致超卖 |
| Lua 原子扣减 | 并发下的 check-then-act 竞态 |
| Redis Stream 异步落库（消费组，失败不 ack 下轮认领） | 写库成为下单瓶颈 / 落库失败丢单 |
| 在途登记 + `TicketInflightReconcileJob` 对账补偿 | 落库**永久**失败时余票只扣不回（见 3.3） |
| `TicketOrder` 的 `@Version` 乐观锁 | 并发更新同一订单（冲突返回 409） |
| `TicketExpireJob` 超时过期 + 回补余票 | 占位不支付长期锁死库存 |
| `AdminConfirmService` 一次性确认码（2 分钟 TTL，验过即废） | 高危管理操作误触 |

### 3.2 智能对话链路（Python）

```
POST /api/chat（SSE）
  → JWT 中间件校验（失败即 401，不进 RAG、不调 Java）
  → 每轮先做一次 RAG 检索，把【参考资料】注入上下文
  → function-calling Agent 循环（最多 4 轮）
      模型返回 tool_calls → 执行 → 结果回注上下文 → 下一轮
  → 12 个工具经 java_client 单一 REST 通道调 Java（透传 Bearer token）
  → SSE 分阶段推前端：think / result / answer / confirm / error（每条事件带 model）
```

### 3.3 异步落库失败的兜底（对账补偿）

Stream 异步落库有个固有缺口：**扣减发生在 Redis，订单却要靠消费端落库**。消费端持续失败（或事件丢失）时，DB 里永远没有这单，而 `TicketExpireJob` 只扫 DB 的 PENDING，扫不到它——扣掉的余票永不回补；占位 TTL（30 分钟）到期后用户还能再买同一车次，**同一张票被扣两次，且 DB 与日志里毫无痕迹**。写 Stream 同步失败时更直接：此前只释放了占位，没回补库存。

三层兜底：

1. **在途登记（写在 XADD 之前）**
   `rv:inflight:{requestId}` = `tripId|seatClass|userId|下单毫秒`（TTL 15 分钟），
   `rv:inflight:idx`（ZSET，score=下单毫秒）供按时间扫描。
   登记先于 `XADD`，因此 XADD 抛异常时能连同**库存**一起还回去。

2. **消费端销登记**
   落库成功后删详情 + 摘索引；并把完成清理作为落库成功的最后一步。

3. **对账任务 `TicketInflightReconcileJob`（每 60 秒）**
   扫 ZSET 中超过宽限期（3 分钟，远大于毫秒级的正常消费延迟）的登记：
   - DB 已有该订单 → 只是消费端清理慢，摘索引；
   - DB 无该订单 → 判定投递失败：**回补余票 + 释放一人一票占位**，并落 error 日志。
   判定时先把登记改写成 `cancelled` 墓碑，**消费端落库前读取该墓碑**，见到就丢弃迟到的事件——
   避免"先补偿、后插单"导致库存与订单对不上。

**实现要点（踩过的坑）**：墓碑必须在**解析校验之后**才写。第一版把墓碑写在了解析之前，结果一条畸形登记会让「墓碑已落、余票未回补」——消费端据此丢弃订单，**票凭空消失，比不做对账更糟**。现在的顺序是：解析校验 → 立墓碑 → 判 DB → 补偿；且补偿抛异常时**回滚墓碑**，交给下一轮重试。这个 bug 是实测时故意注入畸形数据才暴露的。

**残余风险**：判定与消费之间存在极窄竞态（消费端读完墓碑、尚未插入时被判定），宽限期 3 分钟已把它压到可忽略，但严格说未彻底消除——彻底做法是让落库与判定共享一个事务性存储。

## 4. 核心设计：模型决策与确定性执行分离

这是本项目的中心思想，落实在四处：

| 机制 | 做法 | 防的是什么 |
|---|---|---|
| **tripId 溯源** | `buy_ticket` 的 `tripId` 必须命中上一轮查票返回的结果，否则拒绝 | 模型凭空编造车次下单 |
| **两阶段确认** | 模型只预填意向并复述，用户回「确认」后由确定性代码 `_commit_buy()` 真正下单 | 模型自作主张发起写交易 |
| **支付取记忆** | 支付/退票直接取记忆中的 `requestId`，不由模型传参 | 编造参数重复发起写交易 |
| **政策硬校验** | `TicketPolicy.java` 集中裁决：过期车次、一人一票、儿童票 6–14 岁、学生票（学生身份 + 二等座 + 寒暑假窗口）、支付/退票状态机幂等 | 政策判定被模型的幻觉污染 |

`TicketPolicy` 是所有写操作前置校验的唯一入口，Controller 与 Agent 都不散落判断。

## 5. 模型路由

- 业务代码**不出现模型名**，只认配置键：`MODEL_AGENT` / `MODEL_MULTIMODAL` / `MODEL_GEN`（`app/config.py`）。
- 配置键映射到官方模型 id，dev / prod 两档只改配置、不改代码。
- SSE 每条事件携带 `model` 字段，前端展示在回复气泡上。
- 接入 DeepSeek 官网 API，key 走环境变量 `DEEPSEEK_API_KEY`；`JWT_SECRET`（HS256）Java / Python 共用。
- **当前状态**：`MODEL_MULTIMODAL` 已在配置中定义，但尚无业务调用方（多模态目前走本地 WeMM 嵌入，不是多模态大模型）。

## 6. RAG 设计

### 6.1 入库

- 支持 md / docx / doc / pdf；md 按 `#/##/###` 标题分段，docx 按 Heading 样式，pdf 按页。
- **Small-to-Big 两级切块**：句级切块（`max_len=200, min_len=30`）作为检索单元，所属页级原文作为生成单元。
- 每个子块记录 `parent_id / small_text / parent_text / source / page_no / heading / dept_tags`。
- 管理接口支持单文件上传（同名覆盖）、全量重建、删除并清理向量残留。

### 6.2 存储

Milvus Lite 嵌入式集合（`data/rag.db`），`dim=1024`，`AUTOINDEX` + `COSINE`。
嵌入由本地 8001 服务提供：WeMM-Embedding-2B（int8 GPU，MRL 截断至 1024 维）或 bge-m3（CPU），文档内容不出网。

### 6.3 检索：向量 + 中文 BM25 + RRF

```
查询
  ├── 向量检索（Milvus，COSINE，带 dept_tags 标量过滤）→ 排名
  └── 中文 BM25（CJK 重叠 bigram 切词，k1=1.5 b=0.75，页级倒排懒加载）→ 排名
        ↓
     RRF 融合（k=60）
        ↓
   按 parent_id 去重 → 取整页 parent_text → 前缀 "[来源 文件名 第N页 · 标题]"
```

- 中文 BM25 自实现，用 CJK 重叠 bigram 切词，不依赖分词库。
- 混合的理由：向量懂语义但不敏感术语与编号，BM25 反之。
- 用 RRF 而非加权求和：两路分数尺度不同（余弦 0–1，BM25 0–数十），RRF 只用排名，天然免疫尺度差异。

### 6.4 可见性过滤（行级权限）

md 文件顶部 front matter 声明 `dept_tags`，入库时解析并剥离；未声明的默认 `["all"]`（全员可见）。

检索时**两路都过滤，语义必须一致**：
- **向量路**：Milvus 标量过滤 `dept_tags in ["all", "<本部门>"]`（`store.dept_filter_expr()`）
- **BM25 路**：按 `store.visible(dept_tags, 部门)` 过滤

用户没有部门时只能看到 `all`——即"没有部门的人只能看公开文档"。

演示数据 `data/docs/值班与调度规程（综合管理部）.md` 声明了 `dept_tags: 综合管理部`，用于验证该机制**确实生效**（而不是只存在于代码里）。

> ⚠️ 该过滤依赖 JWT 里的 `department`。若演示账号没有部门，过滤会退化成"只返回 all 文档"，受限文档对所有人不可见——机制看起来写了、实际全失效。`DataInitializer` 每次启动会为演示账号补齐部门/职级（幂等，只补空值，不覆盖）。

验证方式：
- 单测 `tests/test_rag_permission.py`：front matter 解析 + 可见性判定 + 过滤表达式（纯逻辑，不需要 Milvus）
- 脚本 `scripts/kb_permission_check.py`：需嵌入服务与已入库数据，按部门分别检索同一问题，比对命中来源

### 6.5 管理权限与操作审计

**两层权限，维度不同，不要混为一谈**：

| 层 | 判据 | 作用 |
|---|---|---|
| 管理层 | `role == ADMIN` | 能否上传 / 删除 / 重建知识库 |
| 检索层 | `department` 匹配 `dept_tags` | 能否在对话中检索到某篇文档 |

知识库管理接口在 `/api/admin/kb/**`，每个接口逐个校验 ADMIN（`routers/kb.py::_admin`），前端菜单与视图同样按 `isAdmin` 隐藏。

每次写操作**以及被拒绝的越权尝试**都落审计（`app/audit.py`，append-only JSONL，默认 `data/audit/kb.jsonl`），字段：时间、用户、角色、部门、动作、目标、结果、详情。**审计写入失败只记 warning，不阻断主流程。**

查询接口 `GET /api/admin/kb/audit?limit=`（仅 ADMIN），前端知识库管理页下方有「操作审计」表格。

设计取舍：Java 侧已有 `action_log` 表，但 Python 不直连业务库（约定只经 REST 调 Java），故审计先落本地 JSONL。若要与 Java 的审计合并成一份，正确做法是在 Java 加审计上报接口由 Python 调用。

## 7. 会话记忆与档案

| 层 | 实现 | 位置 |
|---|---|---|
| 短期记忆 | 最近 10 条保留原文（`RAW_LIMIT=10`）+ 更早内容用 LLM 滚动压缩为摘要 | `app/agent/memory.py` |
| 存储 | Redis 优先（`mem:agent:{user}:{session}`，TTL 3600s），连不上退进程内内存 | 同上 |
| 隔离 | 按 `user_id + session` 隔离，新对话即空上下文 | 同上 |
| 会话档案 | 每轮 user + assistant 全文写 JSON，支持列表/详情/新建/删除/激活 | `app/agent/history.py` |

**降级原则**：摘要压缩失败退化为朴素拼接，不抛错——记忆压缩不该让整轮对话失败。

## 8. 资源预算

Windows 宿主机 16GB + WSL2 内存池 12GB（`.wslconfig`）。所有服务在 WSL2 内。

| 组件 | 内存 | 显存 |
|---|---|---|
| Java（堆 1GB） | ~1.5GB | 0 |
| Python（FastAPI） | ~1GB | 0 |
| 嵌入服务 + WeMM-2B（int8） | ~1.5GB | ~0.6GB |
| Milvus Lite | ~3GB | 0 |
| Redis / MySQL | ~0.8GB | 0 |
| **合计** | **约 8GB / 12GB** | **~0.6GB** |

## 9. 启动顺序

1. WSL2 启动（确认 `.wslconfig` 生效：`wsl --shutdown` 后重启）
2. `infra/`：`docker compose up -d`（Redis + MySQL，首启执行 `init/` 下 SQL）
3. Java：`mvn spring-boot:run`（8080，启动时播种演示数据）
4. 嵌入服务：`uvicorn app.embed.server:app --port 8001`
5. Python：`uvicorn app.main:app --port 8000`
6. 前端：`npm run dev`（5173）

一键脚本见 `scripts/`。

## 10. 已知局限

诚实记录，作为后续改进清单：

| 局限 | 影响 | 改进方向 |
|---|---|---|
| Redis Stream 顶替消息队列 | 演示级可靠性，可能丢消息 | 换 Kafka / RocketMQ |
| Agent 工具调用串行 | 多工具场景延迟叠加 | `asyncio.gather` 并行 + 工具级超时与重试 |
| 知识库为演示规模（22 篇 / 115 段） | 三路检索 Hit@5 均 100%，差异只体现在排序，区分度有限 | 继续扩充语料与评测集 |
| 评测集 36 条、RAGAS 抽样 12 条 | 规模有限，不能替代线上真实分布的评测 | 扩大评测集、补线上埋点 |
| BM25 页级索引全量加载、增删后整体重建 | 规模上去后不可用 | 落盘倒排 + 增量维护 |
| 无 token 统计与成本计量 | 无法核算调用成本 | 在模型层统一埋点，按 task × model 统计 |
| 无长期记忆 | 跨会话不记得用户 | 用户画像结构化 + 历史摘要向量化 |
| RAG 检索失败静默跳过 | 用户无感但答案质量下降 | 显式降级提示 + 相似度阈值拒答 |
| 对账判定与消费插入之间有极窄竞态 | 理论上可能重复补偿一张（`release` 有总席位上限，不会超卖） | 落库与判定共享事务性存储 |
| 前端「铁路管理」未实现 | 后端 `/api/rail/**` 在 UI 不可达 | 补管理页（可选） |
| 会话档案为读-改-写 JSON，无锁 | 同一用户并发对话可能丢更新 | 加文件锁或改追加式存储 |
