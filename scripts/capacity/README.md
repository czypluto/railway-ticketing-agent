# RAG 页索引容量测试

回答一个问题：**语料从演示规模长大以后，页索引还能撑多少？**

`build_page_index` 是纯函数，所以这里**不需要 Milvus、不需要嵌入服务、不需要停主服务**
—— 直接把 22 篇真实语料重组成任意页数喂进去就行。
用 `backend-python` 的 venv 直接跑（`pymilvus` 都不用装）。

```bash
python scripts/capacity/bench.py --pages 100000 --impl new
python scripts/capacity/bench.py --pages 100000 --impl old     # 对比重构前
python scripts/capacity/bench.py --pages 10000 --breakdown     # 看内存构成
python scripts/capacity/candidate_ratio.py --pages 100000      # 候选集占比
```

## 为什么会有这个目录

检索指标在演示语料上**早就饱和了**（22 篇、TopK=5 时向量 / BM25 / 混合三路
Hit@5 全是 100%），从质量指标上看不出任何问题。所以换一个维度量——**规模**。

## 测出来的问题（重构前）

| 页数 | 索引 RSS | 构建 | 查询 P50 |
|---:|---:|---:|---:|
| 5,000 | 118 MB | 0.64 s | 14.0 ms |
| 20,000 | 469 MB | 2.79 s | 58.8 ms |
| 50,000 | 1,173 MB | 7.48 s | 152.9 ms |
| 100,000 | **2,346 MB** | **17.5 s** | **355.5 ms** |
| 200,000（`limit` 上限，外推） | ~4.7 GB | ~38 s | ~700 ms |

三个根因：

1. **`tf` 每页一个 dict** —— 8000 页实测占 95% 内存（23 KB/页，而正文只有 0.9 KB）。
2. **重建在请求路径里** —— `_ensure_page_index()` 在 `retrieve()` 内调用，
   任何 ingest/delete 都触发重建，**下一个用户请求会被阻塞**。
3. **查询遍历全部页** —— `for key in allowed: _bm25(...)`。

## 改成单倒排 + 紧凑数组之后

```python
# 旧：每页一个 dict，10 万页 = 10 万个对象
pages[key]["tf"] = {"退票": 3, "票价": 1, ...}

# 新：一个倒排，postings 是扁平整型数组 [idx, cnt, idx, cnt, ...]
postings["退票"] = array('i', [0, 3, 17, 1, ...])
df = {t: len(p) // 2 for t, p in postings.items()}   # df 免费
```

| 页数 | 内存（前→后） | 查询 P50（前→后） |
|---:|---:|---:|
| 5,000 | 118 → **18.0 MB**（6.5×） | 14.0 → **3.4 ms**（4.1×） |
| 20,000 | 469 → **64.9 MB**（7.2×） | 58.8 → **15.9 ms**（3.7×） |
| 50,000 | 1,173 → **164.1 MB**（7.1×） | 152.9 → **52.6 ms**（2.9×） |
| 100,000 | 2,346 → **333.5 MB**（7.0×） | 355.5 → **134.8 ms**（2.6×） |
| 200,000（外推） | ~4.7 GB → **~0.67 GB** | — |

## 两个必须一起说的 caveat

**① 查询提速是下界，不是上限。**
本目录的合成语料是 22 篇**重组**出来的，常见 bigram 几乎出现在每一页。
`candidate_ratio.py` 实测候选页占比 **9.6%–98.4%**：

| 查询 | 候选占比 |
|---|---:|
| 危险品有哪些 | 9.6% |
| 宠物能不能带上车 | 45.1% |
| 退票手续费多少 | 55.7% |
| 常旅客积分怎么算 | 98.4% |

真实异构语料下大部分查询会接近「危险品」那档，优势更大。
**所以对外说「2.6× 起」。**

**② 构建耗时略增 ~10%**（100k 页 17.5 s → 18.8 s）。
这是用内存换来的取舍，不是白赚。

## 行为等价的保证

重构不能改变检索结果，所以 `tests/test_rag_index_equiv.py` 把**旧算法冻结在测试里**当参照，
用真实 22 篇语料跑 20 个 query × 4 个部门，断言：

- 每页 BM25 分数**精确相等**（`==`，不是近似）
- 排序后 key 顺序**完全一致**

能逐位相等是因为两版都按 `set(query_tokens)` 的顺序对同一页累加同样的项；
候选集变小不影响结果 —— 旧实现里 score 恰为 0 的页本来就会被丢弃。

## 还没解决的

`_ensure_page_index()` 仍然是**全量拉取 + 请求路径重建**（见 `bench.py` 顶部的说明）。
倒排本身省了内存和查询时间，但这两条没变。语料再上一个量级需要：
改增量维护，或把倒排挪到独立检索组件。
